# Extension-as-a-Proxy (EaaP) with LLM-Driven API Inference

## 1. Abstract

This document extends the Extension-as-a-Proxy (EaaP) architecture (RFC-2026-EAAP-01) to introduce automated API discovery and complex client-side state execution. It specifies a pipeline where a Chrome Extension captures raw web application traffic, normalizes it, and delegates it to a Large Language Model (LLM) to infer and generate OpenAPI 3.x specifications on the fly. Furthermore, it defines execution strategies for interacting with Single-Page Applications (SPAs) that require DOM event simulation or dynamic JavaScript execution to fulfill requests.

## 2. Motivation

Modern web applications increasingly rely on complex client-side state, WebAssembly, dynamic cryptographic signatures, and anti-automation mechanisms. Traditional HTTP reverse-engineering requires significant manual effort to map endpoints and replicate client-side logic. 

The extended EaaP architecture solves this by:
1.  **Automating API Discovery:** Replacing manual DevTools inspection with continuous background traffic capture and LLM-driven schema inference.
2.  **Abstracting Execution:** Relying on the browser's native JavaScript engine and DOM to handle complex payload signing and state management, rather than attempting to emulate it in a backend server.

This facilitates rapid, standardized integration with internal, legacy, or undocumented web systems via standard Robotic Process Automation (RPA) principles.

## 3. System Architecture & Components

The updated EaaP system introduces the **Schema Generation Pipeline** and the **DOM Execution Engine** to the existing Go Gateway and Chrome Extension components.

### 3.1 Components

*   **OpenAPI Gateway (Go):** Validates incoming requests against generated OpenAPI schemas, routes payloads via WebSockets, and handles the LLM integration pipeline.
*   **Chrome Extension (Manifest V3):** 
    *   *Observer:* Uses `chrome.debugger` to capture network traffic passively.
    *   *Executor:* Executes synthetic `fetch()` requests or injects DOM events via Content Scripts.
*   **LLM Inference Engine:** A language model pipeline tasked with converting raw HTTP traffic into normalized OpenAPI specifications.

### 3.2 High-Level Workflow

The system operates in two distinct phases: **Discovery** and **Execution**.

#### Phase 1: Discovery & Schema Inference
1.  The user browses the target application normally.
2.  The Extension captures network events via the Chrome DevTools Protocol (CDP).
3.  Traffic is filtered (excluding static assets) and sent to the Go Gateway.
4.  The Gateway aggregates requests, groups similar URL structures, and forwards payload samples to the LLM.
5.  The LLM generates standard OpenAPI 3.0 paths, parameters, and schemas.
6.  The Gateway updates its active routing table.

#### Phase 2: Orchestration & Execution
1.  An external client sends a REST request matching the LLM-generated OpenAPI spec.
2.  The Gateway translates this into an EaaP WebSocket Envelope.
3.  The Extension receives the envelope and dispatches it using the appropriate execution strategy (see Section 4).
4.  The Extension captures the response and returns it via WebSocket to the Gateway.

## 4. Execution Strategies

To support complex SPAs, the Extension MUST support multiple execution strategies defined by the `executionMode` parameter in the request envelope.

### 4.1 Mode: SYNTHETIC_FETCH (Default)
Used for standard AJAX/REST endpoints where the browser automatically handles session cookies.
*   **Mechanism:** The background Service Worker invokes `window.fetch(targetUrl, { credentials: "include", ... })`.
*   **Use Case:** The target endpoint requires standard session persistence without complex per-request payload signing.

### 4.2 Mode: DOM_SIMULATION
Used when requests require in-memory JavaScript variables, dynamic single-use nonces calculated on click, or native event listeners.
*   **Mechanism:** The Service Worker relays the payload to a Content Script running in the active tab context.
*   **Procedure:**
    1.  Content Script locates target DOM elements via CSS selectors.
    2.  Injects values into input fields and dispatches native `input` or `change` events.
    3.  Programmatically triggers UI events (e.g., `element.click()`) to initiate the site's native JavaScript execution flow.
    4.  Monitors the network or DOM mutations to capture the resulting data.

## 5. Automated OpenAPI Inference Pipeline

### 5.1 Traffic Normalization
Before LLM processing, the Go Gateway MUST normalize URLs to prevent schema bloat.
*   *Input:* `GET /api/users/1234/profile`, `GET /api/users/5678/profile`
*   *Output:* `GET /api/users/{param1}/profile`

### 5.2 LLM Prompting Specification
The LLM integration should utilize a strict JSON-output prompt structure. The prompt MUST include:
1.  The normalized URL and HTTP method.
2.  A representative sample of Request Headers and Body.
3.  A representative sample of the Response Body.
4.  Instructions to output *only* valid OpenAPI 3.0.3 YAML or JSON.

## 6. Security and Operational Considerations

### 6.1 Terms of Service & Acceptable Use
Automating interactions with web applications via EaaP may violate the Acceptable Use Policies (AUP) or Terms of Service (ToS) of third-party platforms. This architecture is intended for legitimate System Integration, Robotic Process Automation (RPA), and interacting with systems where the operator has authorization.

### 6.2 Rate Limiting and Traffic Shaping
Because EaaP utilizes a single authenticated browser session, aggressive polling will easily trigger application-layer rate limits or account suspension.
*   The Go Gateway MUST implement request queuing and randomized jitter (e.g., 2000ms - 5000ms delay between actions) to mimic human interaction speeds.

### 6.3 Data Privacy
The Discovery phase captures raw traffic, which may contain sensitive Personally Identifiable Information (PII) or authentication tokens.
*   The Traffic Normalization component MUST sanitize headers (e.g., stripping `Authorization` or `Cookie` values) and redact identifiable user data from payload samples *before* transmitting data to external LLM APIs.

### 6.4 Sandboxing & CORS
The Chrome Extension operates with elevated privileges. To mitigate Server-Side Request Forgery (SSRF) risks, the Extension MUST maintain an explicit allowlist of target domains and reject execution envelopes targeting unauthorized origins.
